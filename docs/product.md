# かたち — 設計

## 何を作っているか

顔写真がなく、チャットもないマッチングアプリ。
見た目とトーク術を判断材料から外したときに、何が残るかを試すためのもの。

## 制約（これが仕様の中心）

| 禁止 | 理由 |
|---|---|
| **写真の一切** | 顔写真だけを禁じても、部屋・持ち物・体型の写真で同じ序列が復活する。画像アップロードの経路そのものを作らない |
| **自由文のチャット** | 会話の上手さが支配的になる。テキストは必ず「特定の問いへの回答」としてしか存在できない |
| **アイコンの選択** | 選べる時点で「盛る」余地が生まれる。診断結果から自動生成し、差し替え不可 |
| **相手の答えを先に読むこと** | 先に読めると、うまい答えを真似る競争になる |

`lib/types.ts` に画像の型はなく、`supabase/migrations/0001_init.sql` に画像カラムはない。
「機能として付けない」ではなく「置き場所がない」形にしてある。

## 前提

**恋愛前提**のアプリ。性別・年齢・場所は絞り込みに使う。

「条件で人を絞る」ことと「顔とトークで人を選ぶ」ことは別の問題なので、
前者は認めて、後者だけを潰す。絞り込めるのは以下の3つだけで、
これ以外の条件検索は作らない。

| 項目 | 持ち方 |
|---|---|
| 年齢 | 生年月日ではなく**生年だけ**。18歳未満は登録できない |
| 場所 | 市区町村ではなく**都道府県だけ**。特定に繋がる粒度を持たない |
| 性別 | 女性 / 男性 / その他・答えない |

**条件は双方向でしか成立しない。** 自分が相手を候補に入れていて、かつ
相手も自分を候補に入れているときだけ、お互いの画面に出る。
片側だけで出す作りにすると、望まない相手からの接触が止まらないため。

候補が0件になったときは、どの条件で何人落ちたかを表示する。
黙って空にしない。

## ログイン

**パスキー（WebAuthn）のみ。パスワードは存在しない。**

- 預かるのは公開鍵だけ。秘密鍵は端末から出ない
- `residentKey: required` なので、2回目からは**名前の入力すら要らない**
- パスワードがないので、パスワード漏洩も使い回しも起こらない

セッションは署名付きクッキーに userId を入れるだけで、サーバ側にセッション表を持たない。
`scripts/e2e-passkey.mjs` が、仮想認証器を使って登録からログインまでを通しで確かめる。

## 何で人と繋がるか

### 1. 同じ問い（毎日）

全ユーザーに同じ問いが1日1問。日付から決定的に決まるので、誰かが有利な問いを選ぶことはできない。

**自分が答えるまで、他人の答えは読めない。** アプリの分岐だけでなく RLS でも縛っている
（`answers_select` ポリシー）。

問いの条件は3つ:
- 気の利いた答えが有利にならないこと
- 見た目・持ち物・肩書きを聞かないこと
- 誰でも30秒で答えられること

`lib/questions.ts` に30問。

### 2. 診断（6軸）

12問・5件法。1軸あたり2問で、片方は逆向きに置いて単調な回答を弾く。

| 軸 | 0 ← → 100 | 相性での扱い |
|---|---|---|
| pace | ひとりの時間 ⇔ 人といる時間 | 近いほど良い |
| plan | 即興 ⇔ 計画 | 違っても成立する |
| depth | 広く浅く ⇔ 狭く深く | 近いほど良い |
| logic | 感情 ⇔ 論理 | 違っても成立する |
| novelty | 定番 ⇔ 新奇 | 近いほど良い |
| expression | 察し ⇔ 率直 | 違っても成立する |

生活のリズムが噛み合うかどうか（pace / depth / novelty）は近さを重く見て、
考え方の癖（plan / logic / expression）は差の減点を半分にしている。
「似た者どうし」に寄せすぎない設計。

**数値は本人にしか見せない。** 他人には図形と言葉でしか伝わらない。

### 3. ハッシュタグ

自己申告のタグ。8個まで。
一致の評価は idf で重みづけしていて、**珍しいタグの一致ほど強く効く**。
「音楽」が同じことより「短歌」が同じことのほうが情報量が大きい。

### 4. かたち（アイコン）

6軸を6頂点の半径に変換して、閉じた滑らかな輪郭を描く（`lib/shape.ts`）。
角張った多角形にするとレーダーチャートに見えて「診断結果の表示」になってしまうので、
中点を通す二次ベジェで丸めている。

色相は軸の組み合わせから決まる。彩度と明度は固定で、どの形も同じ「格」に見えるようにしてある
（派手な色を選べると、それ自体が優劣になる）。

## 相性の出し方

```
総合 = 軸 55% + タグ 30% + 回答 15%
```

回答の一致は形態素解析なしの文字バイグラム重なりなので、意味を理解しているわけではない。
だから重みを意図的に小さくしてある。「同じ問いに何回向き合ったか」の継続性も混ぜている。

**内訳は必ず UI に出す。**「なぜこの人が出てきたのか」を説明できない推薦はしない
（`explain()` が一文にする）。

## おまかせマッチ（今週の人）

**このアプリがいちばん力を入れているところ。**

対象にしているのは「見た目に自信がなく、会話も得意ではないが、恋人がほしい」人。
その人にとって最大の障壁は、実は相手選びではなく **自分から「もっと知りたい」を送ること** だった。
そこを丸ごと肩代わりする。

| 決めごと | 理由 |
|---|---|
| **週にひとりだけ** | 選択肢が多いこと自体が人を消耗させる。1人なら向き合える |
| **両者に同時に出す** | 「送る側／送られる側」の非対称を作らない。誰も勇気を出さなくていい |
| **見送っても相手に伝わらない** | どちらが断っても表示は「今回はご縁がありませんでした」。断られた事実が見える設計は、このアプリが対象にしている人をいちばん傷つける |
| **相手の回答を先に見せる** | ゼロから話しかけるのが最難関。話の糸口を最初から渡しておく |
| **見送りは取り消せない** | 取り消せると「やっぱり」が起きて、相手を待たせることになる |
| **8週間は同じ人を出さない** | 「またこの人か」を避ける |

ペアリングは相性の高い組から順に確定する貪欲法（`lib/weekly.ts`）。
安定マッチングにしていないのは、全体最適より
**一人ひとりに「相性がいちばん高い相手だった」と説明できること**を優先したため。
同点は id 順で割るので、同じ入力からは必ず同じペアが出る。

## 出会ってからの流れ

```
パスキー登録 → 診断 → プロフィール（属性・条件） → 今日の問いに答える
                    ↓
    ┌─────────────┴─────────────┐
    ↓                           ↓
おまかせマッチ              さがす（相性順・理由つき）
週にひとり、両者に同時       自分で選びたい人向け
    ↓                           ↓
 両方が「話してみたい」       「もっと知りたい」を送る
        ※ 送ったことは相手に通知されない
                    ↓
        相互になったら つながり成立
                    ↓
        お題交換（自由文のチャットはない）
        札を選ぶ → 二人とも答える → 同時に開く
```

お題交換でも「相手が答えるまで見えない」を維持している。
先に読んで合わせにいく余地を、どの階層にも作らない。
