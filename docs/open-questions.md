# 決めていないこと

朝に確認したいこと。上から順に、進行を止めている度合いが高い。

## 1. 属性を持たせるか（いちばん大きい）

いまは性別・年齢・地域を **持っていない**。全員が全員の候補になる。

マッチングアプリとして成立させるなら普通は要るが、
「顔以外・トーク以外で繋がる」という趣旨とは正面から衝突する。属性で絞った瞬間、
それは条件検索になる。

考えられる線:

| 案 | 中身 |
|---|---|
| A | 属性を一切持たない（いまの実装）。友達も恋愛も区別しない |
| B | 年齢と地域だけ持つ。性別は持たない |
| C | 全部持つが、**絞り込みには使えず、安全のためだけに使う** |
| D | 全部持って普通に絞り込む |

実装コストはどれも小さい。思想の問題なので判断が要る。

## 2. これは恋愛のためのアプリか

「マッチングアプリ」と言われたが、恋愛前提か、友人・話し相手も含むかで
問いの選び方（`lib/questions.ts`）が変わる。いまは**どちらでも読める**中立な問いにしてある。

## 3. Supabase プロジェクトを作るか

スキーマ（`supabase/migrations/0001_init.sql`）は書いたが、**クラウド側には何も作っていない**。
プロジェクト作成は課金に関わるので、勝手にやらなかった。

いまはローカルのファイルストア（`.data/db.json`）で動いている。切り替えは
`lib/store.ts` の差し替えだけで済むようにしてある。

## 4. 認証

いま認証はない。デモユーザー（`usr_01` みずいろ）に固定されている。
RLS は `auth.uid()` 前提で書いてあるので、Supabase Auth を入れれば噛み合う。

beacon でパスキーを使っていたので、同じ方式にするか要確認。

## 5. アプリ名

`かたち` は仮。パッケージ名は `katachi`。変えるなら早いほうがいい。

## 6. 「もっと知りたい」の上限

いまは無制限。無制限だと「全員に送る」が最適戦略になって、
選ぶという行為の意味がなくなる。1日3〜5件くらいの上限を入れるのが定石だが、
数は運用しながら決めるしかない。

## 7. 課金

未着手。上限を課金で外す形にすると 6 の設計と直結するので、
方針だけ先に決めておきたい。
